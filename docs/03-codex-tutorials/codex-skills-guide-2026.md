# Codex Skills 用法：/skills 机制、技能怎么写、什么时候值得写（2026）

> Skills 机制仍在快速迭代，命令与文件结构以官方文档和 `/skills` 实际输出为准；本文讲通用逻辑。

如果你发现自己每周都对 Codex 重复同一套开场白——「先看规范、再按这个流程做、最后按这个格式交付」——这就是该用 Skills 的信号。这篇讲清机制、判断标准和写法。

废话不多说，结论先放这儿：

1. **Skill = 预置的专业说明书**：把「某类任务的标准做法」写成文件，Codex 干这类活时自动带上，不用每次口头交代。
2. 判断标准：**同一个工作流重复 3 次以上**，就值得固化成技能；一次性的任务不值得。
3. 技能和 AGENTS.md 分工：**AGENTS.md 管全局**（项目是谁、什么规范），**技能管特定任务**（这类活怎么干）。

## /skills 是什么

CLI 里输入 `/skills` 可以查看和管理当前可用的技能。技能机制的本质：**把一段「执行特定任务的专门知识」做成 Codex 可发现、可加载的文件**——当任务匹配时，Codex 按技能里的流程和标准执行，而不是靠通用经验自由发挥。

解决的问题是「重复交代」：没有技能时，你每次都要在任务描述里把流程说一遍；有了技能，一句「按 XX 技能处理这个」即可。团队场景里还有第二层价值：**把资深成员的最佳实践标准化**，所有人的 Codex 都按同一套打法干活。

## 什么任务值得做成技能

按投入产出筛：

**值得**：
- 每周重复的工作流（发版检查清单、季度报告格式、特定框架的 CRUD 流程）
- 有固定质量标准的关键任务（安全审查要点、上线前回归范围）
- 团队多人重复踩坑的流程（分支规范、commit 规范的执行细节）

**不值得**：
- 一次性的临时任务
- 三句话就能在提示词里说清的小约定（放 AGENTS.md 更合适）
- 还在探索、没有稳定做法的流程（先跑熟再固化，否则技能锁死错误姿势）

## 技能怎么写

核心原则：**写给「聪明但不了解你团队的新同事」看的操作手册**。

一个技能通常包含：

1. **名称和适用场景**：什么任务该触发这个技能（描述触发条件，让 Codex 能正确匹配）
2. **流程步骤**：按顺序的操作指引——先做什么、后做什么、每步的产出
3. **标准与边界**：完成的定义、不许碰的地方、异常时怎么办
4. **参考资料**：模板、清单、示例的存放位置

写法要点：

- **指令化**：写「执行 X 前先跑 Y」，不写「注意 Y 很重要」
- **给反例**：说明什么情况不在本技能范围内，避免滥用
- **短**：技能越长，遵循度越低；核心流程一页内，细节链接到清单文件

入门路径建议：先在 AGENTS.md 里把某个重复流程写成小节，用顺了、稳定了，再升级成独立技能——避免一开始就过度工程化。

## 技能、AGENTS.md、提示词的三层分工

| 层 | 管什么 | 生命周期 | 例子 |
|---|---|---|---|
| 提示词 | 单次任务的细节 | 一次性 | 「这次用 Zod 校验参数」 |
| AGENTS.md | 项目全局约定 | 长期 | 技术栈、命名规范、常用命令 |
| 技能 | 特定任务的标准流程 | 长期、可复用 | 「按发版技能执行这次发布」 |

从下往上成长的路径最健康：提示词 → 用多了进 AGENTS.md → 复杂到独立成技能。

## FAQ

Q: /skills 和自定义 GPTs 是一回事吗？

A: 不是。自定义 GPTs 是 ChatGPT 对话产品里的定制助手；技能是编程执行侧的任务知识封装。一个管聊天助手，一个管干活流程。

Q: 技能写多长合适？

A: 核心流程一页以内，超过就拆分或把细节外置成清单文件。技能的敌人是「没人读完」。

Q: 个人用户需要写技能吗？

A: 重复工作流多的（固定格式的周报、固定的代码审查清单）就有价值；偶尔用用的，AGENTS.md + 好的任务描述足够。

Q: 技能会让任务变慢或更费额度吗？

A: 加载技能内容会占用少量上下文，换来的是减少来回试错——净效果通常是省。但堆一堆用不上的技能会稀释注意力，只保留真正高频的。
