# Codex Skills 用法：/skills 机制、技能怎么写、什么时候值得写（2026）

> Skills 机制仍在快速迭代，命令与文件结构以官方文档和 `/skills` 实际输出为准；本文讲通用逻辑。

如果每周都要对 Codex 重复同一套要求——「先看规范、再按这个流程做、最后按这个格式交付」——就该使用 Skills。

1. **Skill = 预置的专业说明书**：把某类任务的标准做法写成文件，Codex 处理这类工作时自动加载，不用每次临时交代。
2. 判断标准：**同一个工作流重复 3 次以上**，就值得固化成技能；一次性任务不值得。
3. 技能和 AGENTS.md 分工：**AGENTS.md 管全局**（项目信息、通用规范），**技能管特定任务**（具体工作怎么做）。

## /skills 是什么

在 CLI 中输入 `/skills` 可以查看和管理当前可用的技能。技能把执行特定任务的专门知识沉淀为 Codex 可识别、可读取的文件。任务匹配时，Codex 会遵循技能中定义的流程和标准执行。

技能解决的是重复说明的问题：没有技能时，每次都要在提示词里重申步骤；配置技能后，输入「按 XX 技能处理」即可。在团队协作中，技能还可以把资深成员的操作经验沉淀为统一标准，让所有人的 Codex 输出保持一致。

## 什么任务值得做成技能

按投入产出判断：

**值得**：
- 每周重复的工作流（发版检查清单、季度报告格式、特定框架的 CRUD 流程）
- 有固定质量标准的关键任务（安全审查要点、上线前回归范围）
- 团队多人重复踩坑的流程（分支规范、commit 规范的执行细节）

**不值得**：
- 一次性的临时任务
- 三句话就能在提示词里说清的小约定（放 AGENTS.md 更合适）
- 还在探索、没有稳定做法的流程（先跑熟再固化，避免提前锁死流程）

## 技能怎么写

基本原则是写成一份给「聪明但不了解团队的新同事」看的操作手册。

一个技能通常包含：

1. **名称和适用场景**：明确触发条件，方便 Codex 准确匹配任务
2. **流程步骤**：按顺序排列的操作指引，包含前后顺序与每一步的产出
3. **标准与边界**：完成定义、禁止修改的范围、异常处理方式
4. **参考资料**：模板、清单与示例文件的路径

编写要点：

- **指令化**：写「执行 X 前先跑 Y」，不写「注意 Y 很重要」
- **给反例**：明确哪些情况不属于本技能的处理范围，避免误用
- **保持简短**：核心流程控制在一页内，细节链接到清单文件；技能越长，模型的遵循度越低

建议先在 AGENTS.md 中将重复流程写成小节，等流程跑顺、稳定后，再拆分成独立技能，避免早期过度设计。

## 技能、AGENTS.md、提示词的三层分工

| 层 | 管什么 | 生命周期 | 例子 |
|---|---|---|---|
| 提示词 | 单次任务的细节 | 一次性 | 「这次用 Zod 校验参数」 |
| AGENTS.md | 项目全局约定 | 长期 | 技术栈、命名规范、常用命令 |
| 技能 | 特定任务的标准流程 | 长期、可复用 | 「按发版技能执行这次发布」 |

常见演进路径：先在提示词中尝试，高频规则沉淀至 AGENTS.md，复杂的标准流程再拆分至独立技能。

## FAQ

Q: /skills 和自定义 GPTs 是一回事吗？

A: 不是。自定义 GPTs 是 ChatGPT 对话界面的定制助手，技能是面向编程执行的任务流程定义。

Q: 技能写多长合适？

A: 核心流程控制在一页以内。超过篇幅时拆分模块，或将细节放入独立的清单文件。

Q: 个人用户需要写技能吗？

A: 存在高频重复流程时（如固定格式周报、特定代码审查清单）值得写；若是低频场景，AGENTS.md 搭配清晰的任务描述即可。

Q: 技能会让任务变慢或更费额度吗？

A: 加载技能会占用少量上下文，但能减少多轮试错，整体通常更省额度。不过应避免堆积无用技能，只保留高频使用的配置。
