# Codex 代码审查实战：/review 用法、审查清单、可信改动怎么产出（2026）

> 审查能力随模型版本提升，但「AI 审查 + 人工复核」的框架不变；本文 2026 年 8 月更新。

代码审查是 Codex 的强项——分析严谨、覆盖面广，但速度偏慢（见[编程工具对比](../01-models-and-tools/ai-coding-tools-comparison-2026.md)）。只把 diff 发给模型让它泛泛地看，很难发挥它的审查深度。

核心要点：

1. 会话内用 **`/review`** 审查当前改动；审外部 PR 贴 diff 或用 GitHub 集成。
2. 提示词指定**审查维度 + 输出格式**（问题/位置/建议/严重度），能明显提高审查质量。
3. **AI 审查替代不了人工复核**：它覆盖面广，但对业务上下文的理解不如人工准确。

## 基础用法：/review

在 CLI 会话里完成一轮修改后，输入：

```
/review
```

它会审查当前会话的代码改动，标出问题。也可以附带明确指令让审查聚焦：

> Review 本次改动，重点关注：安全漏洞、性能问题、边界情况处理。按「问题 / 位置 / 建议 / 严重度」格式输出。

默认审查是全量扫描，指定维度后能做更深入的检查。建议关注的三个维度：

- **安全**：注入、越权、敏感信息泄露、不安全的依赖
- **边界情况**：空输入、超大输入、并发、网络失败路径
- **性能**：N+1 查询、不必要的循环、内存暴涨点

## 审查外部代码（非本会话改动）

不在当前会话里的改动也能审：把 diff 或代码贴进对话（注意脱敏，见[数据安全](../00-ai-fundamentals/ai-data-security-2026.md)），并说明背景：

> 这是准备合入的 PR diff。背景：[什么功能]。重点审查：权限校验是否完整、错误处理是否会吞异常。输出格式：问题/位置/建议/严重度。

审查质量取决于对改动意图的理解。代码逻辑模型自己能看懂，但 PR 的业务目标需要由你提供。

## 审查提示词模板

```
角色：你是资深安全工程师
对象：[diff / 文件 / PR 链接]
背景：[功能意图、影响范围]
重点：[安全 / 性能 / 边界 / 可读性，选 1-3 个]
输出：每个问题按「问题描述 / 代码位置 / 建议修改 / 严重度(高中低)」
要求：只报真问题，不确定的标注「待确认」；没有问题的维度明确说「未发现」
```

最后一条用于控制误报：如果不加限制，模型倾向于把代码风格差异当作风险列出，产生大量无价值的报告内容。

## 人工复核清单

AI 审完后，按顺序核对四项，约需 5 分钟：

1. **高危项逐条验证**：对标为高严重度的问题，逐个核对代码确认是真实缺陷还是误报。
2. **业务规则盲区**：核对未写在代码里的约束（例如特定上线节点、财务计算的精度要求等）。
3. **跨改动影响**：单处改动都正确、组合后可能出现异常的场景。模型看的是局部 diff，人工需要看整个系统。
4. **测试覆盖**：审查报告未提及测试时，要求模型补齐：「针对本次改动补充测试用例」。

## AI 审查的三个盲区

1. **业务上下文缺失**：技术实现正确不代表符合业务需求。如果规则本身定义有误，模型无法识别。
2. **跨仓库/跨系统影响**：模型的分析范围仅限于给定的代码上下文。
3. **「看似正确」的错误**：这类代码逻辑流畅、命名清晰，但运算结果有误。编写自动化测试是主要验证手段（见[工作流实战](codex-workflow-guide-2026.md)的测试先行）。

合理的流程组合是：**Codex 负责广度初筛，人工负责深度核验与最终决定**。

## 实战节奏建议

将审查融入日常开发，不要积压到合入前：

- **每个子任务完成后执行 `/review`**：改动较小、定位问题快，消耗额度也低。
- **合入前执行一次全量审查**：补充完整上下文做深度核验。
- **审查意见直接回喂给模型**：输入「按第 2、3 条建议修改代码」，形成「实现 → 审查 → 修复」的循环。

## FAQ

Q: /review 和直接对话里说「帮我看看代码」有区别吗？

A: `/review` 是专用审查指令，按规范流程扫描；在对话中随口提问，输出质量和深度容易不稳定。重要改动建议用 `/review` 或结构化提示词。

Q: 审查发现的低severity问题要全修吗？

A: 不必。按「立即修复 / 记入技术债 / 忽略」分类处理，逐个修改低优先级问题会拖慢开发节奏。

Q: 能审别的 AI 写的代码吗？

A: 可以，这也是常用方式。同类生成模型容易出现特征相似的问题，审查模型对这类问题较敏感。人工仍需负责最终核验。

Q: 审查消耗额度多吗？

A: 取决于 diff 大小。局部小改动消耗很少；全仓库审查开销较大，应控制调用频次或拆分审查范围（额度机制见[用量上限说明](codex-usage-limits-2026.md)）。
