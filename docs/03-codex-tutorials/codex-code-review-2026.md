# Codex 代码审查实战：/review 用法、审查清单、可信改动怎么产出（2026）

> 审查能力随模型版本提升，但「AI 审查 + 人工复核」的框架不变；本文 2026 年 8 月更新。

代码审查是 Codex 公认的强项——分析严谨、覆盖面广（代价是偏慢，见[编程工具对比](../01-models-and-tools/ai-coding-tools-comparison-2026.md)）。但「把 diff 扔给它说看看」只用到三成功力。这篇讲满配用法。

太长不看版，直接抄结论：

1. 会话内用 **`/review`** 审查当前改动；审外部 PR 贴 diff 或用 GitHub 集成。
2. 提示词指定**三个维度 + 输出格式**（问题/位置/建议/严重度），审查质量翻倍。
3. 铁律：**AI 审查替代不了人工复核**——它扫得广，但对业务上下文的判断不如你。

## 基础用法：/review

在 CLI 会话里完成一轮修改后，输入：

```
/review
```

它会审查当前会话的代码改动，标出问题。也可以带明确指令让审查聚焦：

> Review 本次改动，重点关注：安全漏洞、性能问题、边界情况处理。按「问题 / 位置 / 建议 / 严重度」格式输出。

聚焦指令的价值：默认审查是均衡扫描，指定维度后它会往深处挖。三个高价值维度：

- **安全**：注入、越权、敏感信息泄露、不安全的依赖
- **边界情况**：空输入、超大输入、并发、网络失败路径
- **性能**：N+1 查询、不必要的循环、内存暴涨点

## 审查外部代码（非本会话改动）

不在当前会话里改的代码也能审：把 diff 或代码贴进对话（注意脱敏，见[数据安全](../00-ai-fundamentals/ai-data-security-2026.md)），说清背景：

> 这是准备合入的 PR diff。背景：[什么功能]。重点审查：权限校验是否完整、错误处理是否会吞异常。输出格式：问题/位置/建议/严重度。

给背景的原因：审查质量取决于它对意图的理解。「这段代码在干嘛」它自己能看，「这个 PR 想解决什么」必须你告诉它。

## 审查提示词模板（抄走即用）

```
角色：你是资深安全工程师
对象：[diff / 文件 / PR 链接]
背景：[功能意图、影响范围]
重点：[安全 / 性能 / 边界 / 可读性，选 1-3 个]
输出：每个问题按「问题描述 / 代码位置 / 建议修改 / 严重度(高中低)」
要求：只报真问题，不确定的标注「待确认」；没有问题的维度明确说「未发现」
```

最后一条最重要——**抑制它的「报忧偏好」**：不设这条，AI 审查倾向于把风格问题包装成风险，产出一份看起来勤奋实则噪音的报告。

## 人工复核清单（AI 审完你过什么）

按顺序过四样，约 5 分钟：

1. **高危项逐条验证**：它标的高严重度问题，逐个看代码确认是真问题还是误报
2. **业务规则盲区**：它不知道「这个接口周五前不能上」「财务计算不许四舍五入」这类业务约束——这些只能你把关
3. **跨改动影响**：单点都正确、组合起来出问题的场景（它审的是 diff，你审的是系统）
4. **测试覆盖**：审查报告没提测试？让它补：「针对本次改动补充测试用例」

## AI 审查的三个盲区（为什么不能全自动）

1. **业务上下文缺失**：技术正确 ≠ 业务正确。折扣逻辑算得再准，规则本身就是错的它发现不了。
2. **跨仓库/跨系统影响**：它看到的是给它看的范围。
3. **「看起来对」的 bug**：AI 生成的代码里最危险的类型——逻辑流畅、命名清晰、结果是错的。测试是唯一解（见[工作流实战](codex-workflow-guide-2026.md)的测试先行）。

所以正确的定位是：**Codex 当第一道闸（广度），人当第二道闸（深度和责任）**——两道都要。

## 实战节奏建议

把审查嵌进工作流而不是攒到最后：

- **每个子任务完成就 `/review`**（便宜，改动小、问题定位快）
- **合入前做一次全量审查**（带完整背景的深度审查）
- **审查产出直接回喂**：「按第 2、3 条建议修改代码」——形成「实现 → 审查 → 修复」的循环

## FAQ

Q: /review 和直接对话里说「帮我看看代码」有区别吗？

A: `/review` 是专门的审查指令，会按审查的完整流程扫描；对话里随口让它看，产出偏即兴。重要改动用 /review 或模板化提示词。

Q: 审查发现的低severity问题要全修吗？

A: 不必。按「现在修 / 建技术债跟进 / 不改」三分类处理——全修低优先级问题会拖垮节奏。

Q: 能审别的 AI 写的代码吗？

A: 能且推荐——AI 审 AI 写正是当前的主流用法：生成方和审查方是同一类工具时，审查方对「AI 式错误」的嗅觉反而敏锐。人仍然做最终复核。

Q: 审查消耗额度多吗？

A: 随 diff 大小浮动。小改动审查很便宜；全仓库审查是重任务，控制频率或拆分范围（额度机制见[用量上限说明](codex-usage-limits-2026.md)）。
